# BlockSetu risk-scoring ML service

A small FastAPI service that predicts `Task.riskScore` (0-100) and explains
the prediction with real per-feature SHAP contributions — replacing the
random `riskScore` / `shapFactors` the frontend and backend seed data
currently generate. One gradient-boosted regression model is trained per
department (ENG / S&T / TRD), since each department has a different, and
mostly non-overlapping, feature set.

## Why per-department models

The frontend's SHAP chart already groups risk factors by department (see
`frontend/src/mockData/tasks.ts`'s `SHAP_POOL`). This service reuses those
exact feature names as its schema (`app/features.py`), so a real model's
explanations drop into the existing `ShapChart` component with no frontend
changes.

## Data: synthetic but structured, not random

`app/synthetic_data.py` draws a latent per-asset "neglect" factor
(Beta(2, 3.5) — skewed toward well-kept assets with a long bad tail) and
derives every feature from it plus noise, so features correlate the way
real inspection data would (an old asset tends to also be overdue *and*
defect-prone, not independently random). The ground-truth risk score is a
weighted combination of the normalized features plus a couple of
department-specific interaction terms (e.g. rail age × days overdue) plus
observation noise — learnable, but not a trivial linear fit.

## Setup

```bash
cd ml
python -m venv .venv
.venv/Scripts/activate        # .venv\Scripts\Activate.ps1 on PowerShell
pip install -r requirements.txt

python -m app.train            # trains + saves models/{eng,snt,trd}.joblib + metrics.json
uvicorn app.main:app --port 8000 --reload
```

Current held-out test metrics (`models/metrics.json`, regenerated by
`train.py`):

| Department | MAE | R² |
|---|---|---|
| ENG | ~5.2 | ~0.79 |
| S&T | ~4.0 | ~0.87 |
| TRD | ~4.9 | ~0.81 |

## API

- `GET /health` — which department models are loaded.
- `GET /features/{department}` — the feature schema (slug, label, unit,
  range, kind) a caller needs to build a `/predict` request.
- `GET /metrics` — MAE/R²/train-test split per department (a minimal
  model card).
- `POST /predict` — `{ department, features: {slug: value, ...},
  fillMissingWithDefaults? }` → `{ riskScore, baseValue, shapFactors,
  usedDefaults }`. `shapFactors` is `[{ name, contribution, value }]`,
  sorted by contribution descending — the exact shape of the frontend's
  `ShapFactor[]`. `baseValue + sum(contribution)` reproduces `riskScore`
  (the SHAP additivity guarantee).
- `POST /predict/batch` — same, but takes `[{ id, department, features,
  fillMissingWithDefaults? }]` and returns one result per `id`, with
  per-item errors isolated (one bad item doesn't fail the batch).

Binary/tristate features (`redundancy_available`, `vendor_amc_status`) take
`0`/`1` (and `0.5` for "lapsing" AMC) and are formatted as
`"Available (favorable)"` / `"Current (elevated)"` etc. rather than raw
numbers.

## Wired into the Node backend

`backend/src/routes/ml.ts` proxies `/api/ml/{health,features/:dept,metrics,
predict-risk}` to this service (`ML_SERVICE_URL`, default
`http://localhost:8000`) — start this service before the Node backend if
you want those routes to work; they return a 502 with a clear message if
it's unreachable rather than hanging.

The seed (`backend/src/seed/index.ts`) generates inspection-style feature
values for every task, sends them to `/predict/batch`, and stores the
returned `riskScore`, SHAP `baseValue` and factors on the task (plus the raw
`features`). The frontend's task drawer shows them. If this service is down
while seeding, the seed falls back to heuristic scores and says so.

After retraining (`npm run train` from the root), call
`POST /api/ml/rescore-tasks` on the backend to re-score every task from its
stored features.
